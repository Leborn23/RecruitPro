# 招聘薪资决策台设计

日期：2026-04-18

## 目标

`/salary` 不再只是市场行情展示页，而是招聘流程内的薪资决策台，回答两类问题：

- 面试前：这个候选人是否值得继续推进
- Offer 前：建议给到什么区间

本次范围只覆盖招聘侧薪资决策，不扩展为内部员工薪酬管理系统，也不做完整的 offer 审批流。

## 范围

本次实现包含：

- 市场薪资基准展示
- 候选人期望薪资与岗位市场区间对比
- 基于规则的推进结论
- 轻量 offer 建议区间
- 轻量 offer 记录与备注

本次不包含：

- 内部员工薪资台账
- 调薪审批流
- 多级审批、审批节点、审批历史
- 正式 offer 发放、接受、拒绝的完整流程系统

## 数据模型

### 现有数据

- `market_salaries`
  - 提供岗位 / 城市维度的市场区间基准
- `candidates`
  - 提供候选人基本信息
- `active_positions`
  - 提供岗位标题、部门、地点、筛选要求等

### 新增表

新增轻量表：`candidate_salary_profiles`

字段建议：

- `id`
- `candidate_id`
- `position_id`
- `expected_salary_min`
- `expected_salary_max`
- `current_salary`
- `offer_salary`
- `offer_status`
- `notes`
- `updated_at`
- `created_at`

设计理由：

- 不污染 `candidates` 主表
- 支撑“期望薪资 / 当前薪资 / 建议 offer / offer 状态 / 备注”这组招聘侧字段
- 足够支持当前版本，不提前引入审批流结构

## 页面结构

### 1. 顶部概览

展示 4 个指标：

- 高于市场候选人数
- 可推进人数
- 高风险 offer 数
- 市场库覆盖岗位数

作用：

- 让招聘负责人先看风险和机会分布

### 2. 中间主列表

每一行表示一个“候选人 x 岗位”的薪资判断单元，核心字段：

- 候选人
- 岗位
- 期望薪资
- 市场区间
- 建议区间
- 匹配状态
- 下一步动作

状态仅保留三类：

- `可推进`
- `需谈判`
- `暂缓`

### 3. 右侧详情面板

选中某条记录后展示：

- 候选人期望区间
- 当前岗位市场区间
- 建议 offer 区间
- 风险信号
- 结论说明
- 轻量记录区

轻量记录区字段：

- `offer_salary`
- `offer_status`
- `notes`

## 规则引擎

第一版只用规则，不上模型。

### 输入

- 候选人期望薪资
- 市场最低 / 平均 / 最高薪资
- 岗位信息
- 候选人面试结论（如果已有）

### 输出

- `decision_status`
- `recommended_offer_min`
- `recommended_offer_max`
- `risk_flags`
- `suggested_action`

### 判断规则

#### 规则 1：可推进

满足任一条件：

- 候选人期望区间落在市场区间内
- 候选人期望略高于市场均值，但未明显超出市场上限

输出：

- 状态：`可推进`
- 动作：进入下一轮或准备 offer

#### 规则 2：需谈判

满足任一条件：

- 候选人期望高于市场上限，但在可谈判浮动内
- 岗位紧缺，允许适度溢价

输出：

- 状态：`需谈判`
- 动作：保留推进，建议沟通预算与期权 / 奖金结构

#### 规则 3：暂缓

满足任一条件：

- 候选人期望显著高于市场区间
- 岗位预算明显无法覆盖
- 候选人风险较高且报价偏高

输出：

- 状态：`暂缓`
- 动作：暂停推进或等待预算调整

### 建议 offer 区间

第一版规则：

- 默认锚定市场中位附近
- 候选人面试强、岗位紧缺时向上浮动
- 候选人风险高或岗位非紧缺时向下收敛

## 数据流

### 读取

页面加载时聚合：

- `market_salaries`
- `active_positions`
- `candidates`
- `candidate_salary_profiles`

前端或后端计算出统一的薪资决策视图模型。

### 写入

用户在右侧详情面板修改：

- `offer_salary`
- `offer_status`
- `notes`

写回 `candidate_salary_profiles`。

## API / 代码边界

建议新增一个聚合读取接口，避免页面自己拼太多表：

- `GET /api/salary/dashboard`

返回：

- 顶部指标
- 列表数据
- 过滤所需岗位 / 城市选项

建议新增一个更新接口：

- `PATCH /api/salary/candidate-profile/{id}`

更新：

- `offer_salary`
- `offer_status`
- `notes`
- 期望薪资相关字段

如果现阶段不想先扩 FastAPI，也可以第一版继续由前端直连 Supabase 做读取与写入；但推荐把聚合读取放到后端，便于后续补预算规则。

## 前端实现建议

`/salary` 页面拆成三层：

- `salaryViewModel.ts`
  - 纯规则计算与视图映射
- `Salary.tsx`
  - 页面容器、过滤、加载态
- 轻量子组件
  - 概览卡
  - 列表行
  - 右侧详情面板

这样规则和界面分离，后面要换判断规则时不必重写页面。

## 错误处理

- `market_salaries` 为空：页面显示“暂无市场数据”，但不报错崩溃
- 候选人缺少薪资字段：状态标记为“待补充”
- 岗位找不到匹配市场区间：显示“缺少市场基准”
- 写入失败：保留当前编辑内容并提示失败

## 验证

至少验证：

- 有市场数据、有候选人数据时能正常生成列表
- 候选人期望缺失时不会报错
- 三类状态都能被覆盖到
- 右侧修改后能成功写回
- 空数据时页面可用

2. 实现薪资决策视图模型
3. 改造 `/salary` 页面为“概览 + 列表 + 详情”
4. 接入轻量写回
5. 补验证与空态
